First, the dependency rule needs one adjustment. The example creative.dependsOn = ["project", "people"] conflicts with “feature contexts may depend only on spine contexts,” because people is not in the new five-context spine. The cleaner rule is: every app includes the spine; context-to-context dependencies are allowed only when there is a real schema/contract dependency, and the full graph must remain acyclic. That lets creative → people exist when creative records actually reference talent/people, without forcing every relationship into flow composition.
Second, the proposed acceptance test should say context.dependencies("creative") → ["project","people"]. dependents("creative") means the inverse: contexts that depend on creative.
Third, FUTURE_PRODUCTION_SET must contain explicit canonical table IDs, not labels such as “hardened auth/session/access tables” or “RAG/knowledge tables.” If the intended result is exactly 335 STUBBED + 17 PLANNED = 352, commit those exact 17 IDs.     → registry validation fails
    → CI fails
    → registry cannot publish
    → compiler cannot consume it

ERROR > 0
    → publish fails

WARNING > 0
    → publish permitted with report

INFO
    → advisory only

compiler can consume it
