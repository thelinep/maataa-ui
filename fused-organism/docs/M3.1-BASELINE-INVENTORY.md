## Current render and package boundaries

```text
TLPS manifest page 223

```

- `@tlps/domain-primitives` exports the canvas and 3D scene through its package root. The TLPS application imports that public package entry; it does not implement a second canvas or WebGL renderer locally.
- `@maataa/ui/navigation` supplies the shared application shell. The TLPS theme remains in the TLPS application.
- `Scene3D` is a lightweight WebGL geometry preview. Its `Camera3D` controls the virtual scene viewpoint; it is not a physical camera stream or PTZ device.
- `@maataa/ui/devices` currently contains only a placeholder export file. There is no camera-view component there.
- `packages/maataa-ui/src/domainPrimitives.test.tsx` imports the TLPS domain package for component tests. This is test-level cross-package coupling to review against the intended dependency direction; the TLPS app itself consumes the package as expected.

## State, fixtures, and persistence

```text
SpatialWorkspace mount
  → read localStorage key `tlps:spatial-workspace:layout-draft:v1`
  → validate draft v1, otherwise use starterSpatialDraft
  → controlled CanvasSurface / Scene3D callbacks update React state
  → debounce save to localStorage (250 ms), flush on pagehide/unmount
  → allow JSON export, sample reset, and PNG snapshot download
```

The starter layout contains three 2D objects (entrance, stage, note) and two 3D models (stage box, entry sphere). The draft validator checks the v1 shape, allowed geometry, vector values, and numeric bounds. The three `spatial-draft.test.mjs` cases cover valid draft shape, local save/read, and malformed/unavailable storage. A separate `domainPrimitives.test.tsx` covers basic canvas editing, geometry/transform behavior, and missing-WebGL fallback.

These are browser-local fixtures and user-controlled drafts. They are not TLPS account records, shared workspace state, approved layouts, or server persistence. This inventory did not execute the tests or browser flow; the test files are recorded as existing coverage, not fresh pass evidence.

## Route actors and permission boundary

Flows `TLPS-FLOW-093`, `095`, and `096` associate the selected page with Client, Producer, Executive Producer, Line Producer, Fabricator, and TLPS Admin actors. Their source abilities differ, including view, edit, approve, and capture-evidence abilities.

The current shell stores a selected preview role in `sessionStorage` and filters protected pages by allowed **family**. It does not enforce each flow ability on individual controls, and it does not call server authorization. `SpatialWorkspace` does not pass `readOnly` to either editor, so anyone who can enter the local role preview can edit the local draft. This is explicitly a demo boundary, not an authenticated permission path.

**M3.5 status:** route registration is already present; actor-aware server authorization and action-level permission proof are not.

## Domain contracts and data source

The current flow bindings for `TLPS-FLOW-093`, `095`, and `096` name contexts `creative`, `eventsSpatial`, `evidence`, `marketplace`, and `production`, and explicitly bind `eventsspatial.events`, `eventsspatial.venues`, and `marketplace.vendors`.

The canonical registry also contains reviewed spatial contracts such as `eventsspatial.spatial_projects`, `spatial_layers`, `spatial_objects`, `spatial_layouts`, `exhibition_layouts`, and `cad_models`. These contracts provide plausible structures for a source-backed preview, but the current TLPS fixture does not reference their IDs or load their records. Their catalog table status is `stubbed`, and the flow binding does not explicitly map these spatial tables. Do not claim they are flow-backed or populated by virtue of their contracts existing.

`exhibition_layouts` and `spatial_layouts` appear to represent overlapping layout concepts with different field shapes and links. M3 domain selection should bind to the approved context/flow semantics and resolve this distinction before building an adapter. A candidate vertical slice is a venue + spatial project + exhibition layout + spatial objects, with the exact flow mapping and record source reviewed before implementation.

**M3.4 status:** package-level rendering exists; domain-contract-backed application data is not integrated.

## Experimental camera workstream

- `@maataa/adapter-sdk` exports `createCameraSimulatorAdapter`, a simulator for `camera.ptz` and `camera.read` capabilities.
- The governed command pipeline, recipe, simulator tests, and `apps/reference-control` example exist elsewhere in the kernel.
- The TLPS application does not depend on `@maataa/adapter-sdk`, `@maataa/control`, or `@maataa/recipes`; no simulator state is connected to `SpatialWorkspace`.
- This simulator is separate from `Scene3D`'s virtual orbit camera. The simulator does not establish a live video stream or physical camera support.

**M3 camera workstream status:** reusable simulator and governance foundations exist; TLPS integration is absent. Physical-camera certification remains out of scope and unproven.
