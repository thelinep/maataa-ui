# M3.3 Preflight — Spatial Data and Authorization Map

**Status (2026-10-03):** Local M3.3 contract semantics and conformance slice are implemented and validated. The route now reads, creates, edits, and version-checks in-memory fixture rows. This is not a real API server, authenticated identity, durable persistence, or production authorization; those external gates remain open.

**Baseline:** `feat/m3-tlps-spatial-preview` at `697a5b2406ffd4ad0bed938df99d8ef069ae5a55`.

**Selected route:** `/mobile/223/3d-cad-previz` (page `223`). The route is unchanged. This document records what the current UI and canonical contracts support; candidate mappings below are not a persisted-data implementation or an authorization approval.

## Source findings

- `SpatialWorkspace` currently loads a browser-local version-1 draft from `localStorage`, falls back to starter fixture objects, and edits those objects through `CanvasSurface` and `Scene3D`.
- The role selector is a preview value stored in `sessionStorage`. The route guard filters by page family in the browser. It does not provide an authenticated actor or server authorization.
- The TLPS product brief states that authentication, server-side authorization, account-backed persistence, and operational data services are not supplied. The TLPS app tree contains no API or auth route implementation.
- The shared MAATAA UI includes a generic in-memory RBAC helper, but the TLPS app does not connect it to an authenticated identity source or server policy boundary. It is not server authorization evidence.
- `TLPS-FLOW-093`, `095`, and `096` are all marked `demo-shell` and `productionReady: false`. Their permission declarations explicitly say route, action, field, and tenant enforcement are false and client-filter-only.
- Their context bindings name contexts `creative`, `eventsSpatial`, `evidence`, `marketplace`, and `production`, and tables `eventsspatial.events`, `eventsspatial.venues`, and `marketplace.vendors`. They do not bind the spatial-project, layer, object, layout, or CAD-model tables.
- Existing canonical `eventsSpatial` contracts are available for venues, events, spatial projects, layers, objects, spatial layouts, exhibition layouts, and CAD models. Their existence does not mean this page reads those records.

## Frozen layout ownership decision

The user selected both contracts with distinct roles. `eventsspatial.spatial_layouts` is authoritative for the selected M3.3 route because it requires `spatial_project_id` and carries optional canvas dimensions, `layout_data`, versioning, and the `draft → published → archived` status. `eventsspatial.exhibition_layouts` remains a separate venue/exhibition deliverable: it requires `venue_id`, allows an optional spatial-project link, has `venue_area`, and uses a review/approval-oriented lifecycle.

M3.3 therefore follows `spatial_projects → spatial_layouts`. It does not write `exhibition_layouts`, mirror payloads, or add a new FK. A future spatial-to-exhibition conversion must be an explicit workflow. The current exhibition contract has no `spatial_layout_id` relation, so API code must not invent lineage between those records.

The canonical table contract does not define the internal `layout_data` JSON shape. The API DRAFT freezes a MAATAA-authored local payload structure directly from current `canvasItems` and `models`: a 1200×760 top-left-origin 2D canvas plus 3D primitive models. It rejects unknown properties and invalid bounds. Renderer, camera, transient selection, viewport, shell, and export artifacts remain outside persistence. This proposal changes no canonical table contract. Create starts `version_number` at 1; accepted saves increment that same row once. PATCH allows only `name`, `canvasWidth`, `canvasHeight`, full-replacement `layoutData`, and required `expectedVersion`. A stale version returns 409 `SPATIAL_LAYOUT_VERSION_CONFLICT` with no write, increment, merge, or retry.

## API Studio implications

The supplied API Studio assessment is treated as architecture input, not proof that these capabilities already exist or approval to deploy them. Repository checks support its main boundary findings:

- Admin `PRODUCT.md` says the API contract, authorization model, and live-configuration workflow are open decisions.
- Admin `README.md` says auth and permission adapters are host seams; the preview does not mint/store JWTs or enforce server authorization, and protected APIs still need server enforcement.
- No dedicated API Studio UI, canonical API IR package/schema, OpenAPI import/export surface, or request lab was found. An app-local DRAFT proposal schema/validator and a fixture-only spatial conformance host now exist; neither is a production API runtime nor a canonical API Studio implementation.
- API and Identity table contracts describe possible data structures; they do not provide running API-key, webhook, session, or authorization services.
- The discovered `/api/activities` and `/api/permissions/check` strings are not adopted as host APIs: no matching server handlers were found in this repository.

Keep three responsibilities separate:

1. **API Studio** authors, validates, simulates, and records evidence for API contracts. Its output should be a deterministic MAATAA API IR; OpenAPI can be an interchange projection.
2. **TLPS host runtime** executes requests, authenticates actors, enforces tenant and action policy, and persists domain records.
3. **Environment binding** connects a reviewed contract to a verified runtime/environment. A declared contract or local simulation does not establish a live service.

The API IR proposal may carry operation identity, method/path, flow and actor references, request/response/error contracts, declared data reads/writes, authorization/audit policy, and provenance. Base URLs, verification state, and evidence hashes belong in separate runtime bindings. This is a proposal for scope; no IR schema or public package is implemented by this document.

## Revised M3.3 sequence

The previous handoff treated a pre-existing server as a prerequisite for all M3.3 work. That was too broad. Contract design and local conformance work can be separated from production runtime integration:

| Slice | Work | Gate |
|---|---|---|
| M3.3A — domain mapping decision | **Complete:** bind this route to `spatial_projects → spatial_layouts`; retain `exhibition_layouts` for venue deliverables and later explicit conversion. | User decision recorded; no dual writes and no new schema relation. |
| M3.3B — API contract | **Frozen as MAATAA-authored DRAFT for local conformance.** Includes canonical bindings, editor-derived payload schema, query semantics, PATCH, error mappings, permissions, and version conflict rules. | Deterministic contract hash; proposal and request/response/error schemas compile; canonical table/flow source hashes match. Real host identity remains external. |
| M3.3C — local reference host | **Implemented:** in-memory fixture list/get/create/PATCH; actor and tenant checks; strict request validation; compare-and-swap version checks; deterministic fixture response. | `LOCAL_CONFORMANCE_SIMULATION` / `FIXTURE_DATA` labels. No durable storage, real authentication, transaction guarantee, or production authorization. |
| M3.3D — UI adapter | **Implemented:** `/mobile/223/3d-cad-previz` edits and saves through the fixture host; the same row version increments; errors preserve local edits and disclose conflicts. Browser-local demo editor stays separate. | Route is unchanged; local fixture data resets on refresh and never touches `localStorage`. Camera simulator remains a separate runtime adapter. |

The DRAFT operation paths are proposals, not a frozen API naming convention. Snapshot/export is excluded from this contract because the current route only creates local derived artifacts and has no source-backed server snapshot resource or export permission. Exhibition review/approval operations are also excluded.
